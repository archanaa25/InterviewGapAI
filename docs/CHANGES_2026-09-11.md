# Changes — 2026-09-11

Session goal: reduce intake latency (resume extraction → analysis → planning),
make failures fail cleanly instead of hanging or leaking a raw traceback, and
add DeepSeek as an alternate provider. Then reviewed the question-selection
stage against a proposed agentic-loop diagram (see
[Notes](#question-selection-is-not-agentic) below) and implemented the
deterministic half of what that diagram wanted — topic-redundancy handling
(section 6) — rather than an LLM-in-the-loop rewrite.

## 1. Latency: analyzer fan-out, planner digest, lighter extraction model

**`src/resume/analyzer.py`, `src/resume/analyzer_prompts.py`**
Resume analysis used to ask one model call for all 7 competencies plus the
summary in one response — the stage cost as much wall time as the sum of
everyone's output. It now fires 8 concurrent calls (one per competency, one
for the summary) via a `ThreadPoolExecutor`, each carrying its own copied
observability context so the child spans still nest correctly. Measured
**8.3s → 3.2s** (both arms on `gpt-5.4`, isolating the shape change from any
model change).

**`src/planning/interview_planner.py`, `src/planning/prompts.py`**
The planner used to read the full `ResumeAnalysis` JSON (every evidence item
and its source, which the allocation decision never uses) and asked the model
to restate `difficulty_distribution`/`total_questions`, which are sums of its
own per-competency numbers. It now sends a compact evidence digest and derives
the totals in code. On a fast model this measured ~0 latency change (output
tokens aren't the bottleneck there); its real, measured payoff was
**reliability**: 7/10 → 10/10 successful plans on `gpt-5.4`, because a plan
whose restated summary disagreed with its own targets was a real failure mode
that no longer exists.

**`src/resume/extractor.py`**
Extraction is transcription into a schema — it spent zero reasoning tokens
even on the largest model. Default model changed to `gpt-5.4-mini`
(`RESUME_EXTRACTION_MODEL` env override still wins). Combined with the above,
measured total intake: **16.3s → 11.6s** (−28%).

**`scripts/evaluate_intake_latency.py`** (new)
Harness that runs the pre-change and current pipeline shapes side by side
against the same fixture resumes in one session, and writes
`data/eval/intake_latency_report.json` with per-stage before/after seconds,
token counts, completion rate, a per-model request-latency floor, and a
plain-English `change` + `reason` for each stage. Includes an `observations`
block covering three findings that came from watching real runs, not from the
numbers alone (see the file for detail):
- the planner digest's real payoff is reliability, not latency, on a fast model
- `gpt-5.6` was measurably degraded during this session (503s, 5–9s floor)
- a pre-existing planner arithmetic bug surfaced and was fixed alongside this work

## 2. A pre-existing planner bug, found while testing the above

The planner occasionally allocates competency question counts that sum to 9
(or 11) instead of 10 — an arithmetic slip, not a judgement call. It crashed
`scripts/run_intake.py` on `candidate_08` three attempts running.

**`src/planning/interview_planner.py`**
Added a bounded repair loop (`PLANNING_ATTEMPTS`): on a failed total, the
planner is shown its own rejected per-competency breakdown plus a directional
correction ("add 1 question, to the competency with the highest probe
priority") and asked again. All 10 fixture candidates now build a valid plan
on `gpt-5.4`.

## 3. Two real bugs found live, from a genuine account failure

Reproducing "still slow" surfaced that the OpenAI account had **zero credit
balance** (`insufficient_quota`). That's a billing issue, not something code
fixes — but it exposed two real defects in how failures were handled:

**`src/llm_retry.py`** (new)
`call_with_retry()` distinguishes failures a resend can fix (5xx, dropped
connection, an ordinary 429) from ones it can't (`insufficient_quota`,
`credit_balance_exhausted`, `billing_hard_limit_reached` inside a 429 body) —
the latter now raises immediately instead of paying the SDK's own backoff
first. All three stage clients set `max_retries=0` and route through this.
Also treats a `pydantic.ValidationError` raised inside `responses.parse`
itself as retryable — the flake hit while testing DeepSeek (see below).
6 unit tests in `tests/test_llm_retry.py`, including the literal
`insufficient_quota` case reproduced from the live failure.

**`ui/gateway.py`, `ui/app.py`**
The failure's full traceback — including a billing URL from the provider
response — was dumping raw to the terminal via a stdlib `logging.exception()`
call with no configured handler. `ui/app.py` now calls
`configure_observability()` at startup (the project's own documented pattern,
previously never wired into the UI). `ui/gateway.py` now logs the error
**type** only via `log_event`, matching this project's own stated telemetry
contract ("exception messages and tracebacks are not emitted"). Verified: the
same failure now produces one clean JSON line instead of a stack trace.

## 4. Upload prefetch

**`ui/gateway.py`, `ui/app.py`**
Resume extraction depends only on the uploaded bytes, so it now starts the
moment the file lands (`prefetch_resume`), rather than waiting for the
candidate to click "Prepare interview plan." The click collects the
already-running (or already-finished) result instead of starting fresh.
Keyed by file content hash so ordinary Streamlit reruns don't restart it.
2 new gateway tests cover collection and failure-hiding through the prefetch
path specifically.

## 5. DeepSeek as an alternate provider

**`src/llm_client.py`** (new)
`build_client(default_openai_model)` returns a client and default model for
either OpenAI or DeepSeek, selected by `LLM_PROVIDER` (`openai` default,
`deepseek` switches to `DEEPSEEK_API_KEY`/`DEEPSEEK_BASE_URL`/`DEEPSEEK_MODEL`,
already present in `.env` but previously unused). All three stage files
(`extractor.py`, `analyzer.py`, `interview_planner.py`) now call this instead
of constructing `OpenAI(...)` directly; an explicit per-stage model env var
still wins over either provider's default.

Live-tested end to end on DeepSeek (`deepseek-chat`), real API calls, through
the actual project modules: extract 3.2s, 7-way analysis fan-out 4.1s —
both markedly faster than OpenAI's current (degraded) numbers. One real
finding: DeepSeek's structured-output enforcement is looser than OpenAI's —
hit one case where it returned the JSON *schema* instead of filled data (now
covered by the `call_with_retry` fix above) — and the planner's arithmetic
repair loop needed more attempts to converge on DeepSeek (7/10 fixtures
cleared within 3 attempts, vs 10/10 on `gpt-5.4`; 6 attempts cleared all 3
remaining cases in a follow-up test). `PLANNING_ATTEMPTS` was left at 3;
raising it for DeepSeek specifically is an open option, not yet applied.

## 6. Question selection: topic-redundancy check (Tier 1)

**`src/interview/question_selector.py`, `tests/test_question_selector.py`**

Follow-up to the review below, which found the selector's dedup was
`question_id`-only and therefore blind to two *different* questions testing
one piece of knowledge. Implemented the deterministic fix rather than an
agentic loop, for the reason the review gives: this stage is a fixed,
high-volume, auditable slot-fill — the case the corpus's own
`AGENT-FUND-INT-001` rubric says to keep deterministic.

**What it does.** Before accepting a retrieved candidate, `_redundancy_reason`
checks it against every question accepted so far in the interview (not just
the current slot — the motivating pair sat in two different difficulty slots
of one competency) on two signals, both read from corpus records already
loaded, with no extra retrieval and no model call:

1. **Same `sub_competency`** as an already-accepted question.
2. **More than `REDUNDANCY_CONCEPT_OVERLAP` (0.5)** of its `must_have`
   concepts already covered by an accepted question — catches duplication
   that crosses sub_competencies.

**Why both signals, and why sub_competency is primary.** The pair that
prompted this work — `AGENT-FUND-BAS-002` ("what justifies an agent") and
`AGENT-FUND-INT-001` ("when is deterministic preferred") — shares
**zero** literal must-have concept strings, because they are inverse framings
of one trade-off. A concept-overlap check alone provably would not have caught
it; this was verified against the real corpus before settling the design.
Sub_competency is what sees it. Concept overlap is kept as the second signal
for duplication filed under different sub_competencies.

**Why redundancy is a preference, not a rule.** An unfilled slot aborts the
entire intake at the gateway ("No partial interview was started"), and the
corpus has genuinely thin pools — the module's own comment notes `ai_security`
and `python_software_engineering` each hold a single advanced question. So a
candidate flagged as redundant is *deferred*, not dropped: kept whole
(record + retrieval hit) so it can be admitted later without a second
retrieval call, and `used_ids` is deliberately left untouched so a later slot
can still take it on its own merits. If a slot cannot be filled any other way,
`_admit_deferred` accepts it and appends a warning naming exactly what it
repeats and why it was accepted anyway. Verified on the real corpus: a plan
demanding 4 advanced RAG questions exhausts the distinct RAG sub_competencies
and correctly admits one repeat with a warning rather than under-filling.

**One behaviour worth knowing:** because difficulty fallback runs *before*
the deferred pile is admitted, the selector prefers a different topic at an
adjacent difficulty over the same topic at the requested difficulty. That is
deliberate and consistent with the module's existing rule that "the competency
being probed matters more than its difficulty" — it surfaced as a test failure
and was confirmed as correct rather than patched out.

Measured on the real corpus with a plan allocating agentic_ai across basic +
intermediate: previously both slots could land in `agent_fundamentals`; now
they resolve to `agent_design_patterns` + `agent_fundamentals`, all 10 slots
filled, no warnings.

4 new tests (`QuestionSelectorRedundancyTests`): prefers an unused
sub_competency, catches cross-sub_competency concept repeats, admits a repeat
rather than under-filling, and confirms a deferred candidate stays available
to a later slot.

## Question selection is not agentic (review only, no code changed)

Traced `src/interview/question_selector.py` against a proposed
inspect/decide/retrieve-again/repair loop. It's a deterministic single pass:
prefetch every bucket concurrently, take top-ranked unused hits in order,
fall back to an adjacent difficulty only when a pool is empty, record any
shortfall, and let the caller (`ui/gateway.py`) refuse to start an interview
on any unfilled slot. No LLM call exists anywhere in that file. Concretely:
similarity dedup is exact-`question_id`-only (it does not catch two
*different* questions that test near-identical concepts — which is exactly
how the redundant agent-vs-deterministic question pair got into an earlier
generated plan); there is no coverage-quality judgment of retrieved results;
and there is no repair loop — an unfilled slot aborts the whole intake rather
than being repaired. This matches the project's own stated design
("a balanced, non-adaptive interview plan") rather than being an oversight.
